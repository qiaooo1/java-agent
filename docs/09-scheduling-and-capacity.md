# 并发调度与资源控制

## 三层准入

| 边界 | 配置与默认值 | 作用 |
|---|---|---|
| 单用户在途任务 | `MAX_INFLIGHT=10` | 提交事务锁定用户行，限制排队和执行任务总数，超限返回 429 |
| 每 Worker 的执行入口 | `WORKER_CONSUMERS=2` | 固定 Rabbit 消费者数量、最大并发相同，`prefetch=1`，不自动增加执行线程 |
| 跨 Worker 的逻辑执行槽位 | `USER_CONCURRENCY=2`、`PROVIDER_CONCURRENCY=8` | Redis Lua 同时检查用户与全局容量，Redis 故障或响应不确定时不启动执行 |

Compose 将这些配置显式传入对应服务。实例消费者数与用户共享上限分别配置，避免将增加消费者误认为增加用户或模型容量。新属性名是 `workbench.user-concurrency`，旧 `workbench.worker-concurrency` 仅作为未设置新属性及环境变量时的兼容回退。所有 Worker 必须使用一致的共享容量配置，非正数上限在启动时拒绝。

任务通知到达后先查任务状态和数据库的 `available_at`；未到执行时间的旧通知直接确认，不申请容量。通过时间检查只是候选资格，Redis 申请成功后仍须通过任务行锁领取，重复通知只有一个执行者可以创建尝试。竞争失败者归还自己的 token。

## 容量等待与可靠重调度

用户或全局容量不足分别返回 `USER_LIMIT`、`PROVIDER_LIMIT`。Worker 不立即 NACK 热重投，而是在任务行锁内完成以下事务后 ACK：

1. 更新 `RETRY_WAIT`、下一次可执行时间和容量等待次数。
2. 写入完整 `capacity_wait` 事件，记录 `reason`、`delayMillis`、`availableAt`、`deferrals`。
3. 创建相同到期时间的 Outbox 通知，稍后由发布器发送。

同一等待窗口内的重复通知不再次增加等待次数或创建通知。事务失败则不 ACK；既有消息退避重投。提前到达的旧通知不改变已持久化的新安排，执行与结算依然按原有数据库租约和 fencing 校验进行。

第一次等待为随机 1–2 秒，后续窗口为 2–4、4–8、8–16、15–30 秒，达到上限后保持 15–30 秒。随机抖动用于分散重试，不保证严格公平或 FIFO。容量等待次数存于 Flyway V3 新增的 `capacity_deferrals`，最多记到 31；它不占用 `attempt_no` 或最大执行尝试数，真正领取成功时才清零。

原来的固定两秒等待在容量持续不足时容易反复集中竞争。新策略减少持续饱和时的重试频率，代价是容量释放后，已有等待任务最迟可能在约 30 秒后再试，另外还受发布周期、MQ 和执行条件影响；不承诺立即唤醒。等待事件可通过普通事件接口及 SSE 回放，页面识别等待状态，不新增虚假的执行步骤，也不把容量等待计入已结束尝试的执行耗时。

## 槽位与资源生命周期

每次消费生成独立 token。用户和供应商两个 Redis 键使用同一 hash tag，Lua 在一次原子执行中清理过期成员、检查两个上限、创建占位。释放必须同时匹配用户侧成员和 token，错误用户即使拿到另一用户的 token 也不能删掉全局槽位。

槽位有效期为 30 秒，正常执行每 5 秒续约；两侧任一成员缺失或已过期都不能续约复活。容量申请响应丢失时，Worker 不领取任务，会尝试清理本次 token 并退避重投；释放失败由 TTL 兜底。模型客户端、工具线程池和心跳的清理覆盖执行初始化失败路径。

Redis 控制的是应用认可的逻辑执行容量。底层 HTTP 或工具不响应取消时，短时间仍可能存在旧调用；本次没有增加硬隔离进程或证明远端调用立即停止。数据库租约和 Redis 槽位仍是不同职责，前者决定谁有权写任务结果，后者决定是否允许开始新的执行。

## 验证与边界

- `TaskStoreTest`：并发重复等待只生成一次有效安排；退避与计数持久化；Outbox 写入失败回滚状态和事件；取消后不重调度；并发不同任务不能突破在途上限。
- `TaskConsumerTest`：等待落库先于 ACK；未到期通知不占槽；领取竞争失败释放容量；申请结果不确定时清理并 NACK；等待事务失败不得 ACK。
- `RedisSlotsIT`：真实 Lua 下的 64 路全局竞争、32 路单用户竞争、错误归属释放、过期回收和缺失成员禁止续约。默认 `integration` profile 使用 Redis 7.2.4 容器，亦可由独立 Redis 脚本驱动。
- `scripts/progress.test.cjs`：容量等待的实时状态不新增执行步骤，不延长已结束尝试的计时。

Windows 已安装 Redis 时可独立验证 Lua，不必启动整套 Compose：

```powershell
node scripts/redis-slots-smoke.mjs --redis-server "G:\new redis\redis-server.exe" --offline
```

替换为本机 Redis 可执行文件路径；`--offline` 需要已有 Maven 缓存，不加则按 Maven 正常解析依赖。脚本创建随机本地端口，仅监听 `127.0.0.1`，关闭持久化，退出时停止自己启动的子进程，不连接已有 Redis、不清空其他实例。测试只清理自己生成的随机 token，日志在 `target/redis-slots-smoke/`。

本次没有实现严格按用户公平的队列、全局积压条数限制、抢占调度、供应商 QPS 限额或吞吐量基准。增加 Worker 时还需核算每实例 12 个数据库连接、心跳线程、工具线程和上游限额。并发正确性测试中的请求数不能作为项目 QPS 或模型完成吞吐的结论，实际结果见[维护日志](maintenance-log.md)。
